# Working in this repository

## What this project is

Ibex Cairn is an enterprise SaaS platform that migrates integration estates (BizTalk, MuleSoft, later TIBCO/Boomi/IIB) to Azure. Its differentiator is **cost-driven target placement**: deciding which Azure service each flow belongs in, priced from a live rate card, before any code is generated.

Read [docs/00-vision.md](docs/00-vision.md) first. It is short and it is the whole argument.

## Current state

Documentation only. No implementation. Do not scaffold code, create package manifests, or start a build until [ADR-0001](docs/adr/0001-fork-logicapps-migration-agent.md) is resolved — the entire architecture depends on whether the upstream licence permits a commercial fork.

## Load-bearing decisions — do not quietly reverse these

These are recorded as ADRs and each one was a deliberate choice with a rejected alternative:

1. **The language model never produces a cost figure.** It classifies ambiguous flows and writes rationale prose. Every number comes from the priced model. A plausible-looking wrong number is the worst failure this product can have. ([ADR-0004](docs/adr/0004-llm-never-produces-cost-figures.md))
2. **Engines communicate through versioned typed artefacts, never through chat.** Each engine reads named artefacts from the case store and writes its own, like a build pipeline. ([ADR-0003](docs/adr/0003-artifact-store-not-chat.md))
3. **The target is the whole Azure estate, not Logic Apps.** Any design that assumes a single emitter is wrong. ([ADR-0002](docs/adr/0002-multi-target-not-logic-apps-only.md))
4. **The POC contains no code generation.** Engines 0–3 only — assessment, placement, cost, diagrams. It is the first sellable unit precisely because it does not depend on conversion accuracy. ([ADR-0005](docs/adr/0005-poc-scope-assessment-wedge.md))
5. **Diagram topology is derived from the graph, never generated by a model.** An invented edge in an architecture diagram survives review, because diagrams are trusted more than the prose around them.

## Conventions

- **Engine names stay literal** — `Placement & Cost Engine`, not a codename. The architecture documents are sales assets; cute component names make them unreadable.
- **Animal codenames belong to releases**, not components, following the Ubuntu pattern (adjective + alliterating animal).
- **Cost figures in documentation must be labelled** as illustrative model output, never presented as quotations. Production rates come from the Azure Retail Prices API for the customer's region.
- **Never put `BizTalk`, `MuleSoft`, `Mule`, or `Azure` in a product, package or module name.** Those are Microsoft and Salesforce marks. Descriptive use in prose is fine; naming is not. This also protects the Azure Marketplace listing path.
- Prefer British spelling in prose, matching the existing docs.

## Planned stack

TypeScript for the forked core (parsers, IR, emitters) so upstream merges stay tractable. Durable Functions for the orchestrator — dogfooding the platform we recommend is the most persuasive reference architecture available. Claude API behind an `ILlmProvider` abstraction, with the VS Code LM API retained as an optional local provider.

## Sensitive material

Case workspaces contain customers' proprietary integration source code and, where the tracking database is connected, their message volumetrics. `.gitignore` excludes `cases/`, `workspaces/` and `*.msi`. Never commit a real customer artefact, a rate card containing account identifiers, or a tracking-database connection string.
