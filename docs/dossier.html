§ 01

Thesis

The hard part of moving fifty BizTalk applications to Azure is not rewriting the orchestrations. It is deciding, per flow, which Azure service it should become — and being able to defend that decision with a number.

Every tool in this market treats migration as translation: read the source artefact, emit the equivalent target artefact. That framing quietly assumes the target is already chosen. In practice a BizTalk estate contains a content-based router that should become three Service Bus subscription rules and no compute at all; a nightly file sweep that should become a timer-triggered function; a partner EDI exchange that has no option other than Logic Apps Standard with an Integration Account; and a high-volume SAP feed whose Azure bill differs by three orders of magnitude depending on whether it runs through a managed connector or a native client.

Translate all of those into Logic Apps and the migration will succeed technically and fail financially. So the tool proposed here inverts the usual order of operations: decide and price the placement first, generate code second, and prove behavioural parity before anything is promoted.

Three source→target pairs are in scope, in this order: BizTalk → Azure (the whole Azure estate), MuleSoft → Azure, and later BizTalk → MuleSoft — which is only reachable because the intermediate representation is genuinely platform-neutral rather than an Azure-shaped funnel.

§ 03

Why the gap is real

Forking Microsoft's agent is the right call, so it is worth being precise about what it does not do — these are structural limits, not missing features.

The target is hardcoded

The conversion stage emits workflow.json, connections.json and .NET local functions. There is no representation of the question "should this be a workflow at all?" A flow that ought to be a Service Bus subscription rule with zero compute has nowhere to land.

MuleSoft is a stub

Documented support is mule-*.xml and pom.xml, marked "in progress, not yet available." Real Mule projects carry subflows, error-handler hierarchies, property placeholders and environment configs, connector configs, MUnit tests, and DataWeave everywhere. That parser is a substantial build, not a gap-fill.

It cannot be a SaaS in its current shape

The intelligence lives in GitHub Copilot agents driven through the VS Code Language Model API. That makes a Copilot subscription a hard dependency, puts the engine on the developer's laptop, and rules out the regulated customers who most need migration help. Lifting the deterministic core out of vscode is the single most important structural move in this whole plan.

Extension stops at Discovery

External parser extensions register through a plugin API but, per Microsoft's own documentation, only cover the Discovery stage. Planning and conversion require contributing a built-in parser into their repository. A commercial product cannot depend on upstream merge cycles.

Positioning consequence Microsoft owns both the destination platform and a free tool that converts to it. Competing on conversion fidelity is competing on their turf with their roadmap. Competing on multi-target placement, priced economics and parity evidence is competing where they have chosen not to play.

Six commitments hold this together, and each one is a decision that could reasonably have gone the other way:

  1. The deterministic core leaves VS Code. Parsers, IR, and stage logic become a standalone TypeScript library with zero vscode imports. The extension becomes one client; the SaaS API becomes another.
  2. The Copilot LM API is replaced by a provider abstraction — ILlmProvider over the Claude API server-side, with the VS Code LM API retained as an optional local provider. The 13 Markdown skills survive unchanged as prompt assets.
  3. The IR gains a targetPlan layer so target choice is data, carrying a chosen composition, a rationale and a confidence — rather than being implied by whichever emitter happens to run.
  4. Placement becomes an explicit engine with its own policy, its own inputs and its own approval gate (§07).
  5. Emitters are template-plus-LLM, never LLM-alone. Structure comes from templates; the model fills the parts that genuinely vary.
  6. Golden-message replay is a product feature, not a testing afterthought (§14).
§ 05

The intermediate representation

The forked IR is better than expected. It models a flow as a DAG — actions declare predecessors through runAfter — across eight primary sections (metadata, workflow, triggers, actions, variables, connections, schemas, maps) plus supporting sections for messageProcessing, endpoints, correlation, errorHandling, rules, B2B, observability, dependencies, gaps and extensions.

Two design details make it worth adopting rather than replacing. First, layered isolation: platform-specific detail lives in sourceMapping and destination detail in targetMapping, so neither pollutes the core model. Second, a normalised vocabulary already reconciled across eight platforms.

The neutral vocabulary is what makes BizTalk → MuleSoft reachable later, not just BizTalk → Azure.

The one addition we make

The upstream targetMapping field describes a Logic Apps destination. We generalise it into a targetPlan: per flow and per action, the chosen Azure composition, the alternatives that were considered and rejected, the constraint that eliminated each one, the priced cost curve, and a confidence score. Placement stops being an implicit property of the code generator and becomes a reviewable, versioned artefact that a human approves.

§ 07

Cost-driven placement

This is the engine that makes the product defensible. Six steps, in this order, because getting the order wrong produces confident nonsense.

STEP 0
Disposition
12-month traffic per artefact → retire / consolidate / migrate / rewrite, with evidence attached.
STEP 1
Volumetrics
Messages/month, avg & p95 size, peakiness, duration, retry rate. Measured or declared — never assumed silently.
STEP 2
Archetype
Classify the flow, then emit candidate compositions: trigger + compute + state + exposure.
STEP 3
Constraints
Hard filters that override price: size, ordering, VNet, latency, EDI, adapters, residency.
STEP 4
Price
Live rate card × volumetrics for every surviving candidate. Curves, not point estimates.
STEP 5
Pack
Bin-pack flows onto shared hosts and one landing zone, subject to isolation rules.

Step 0 comes first for a reason

BizTalk hands you the disposition evidence for free. BizTalkDTADb holds tracking history per receive port, send port and orchestration; BizTalkMsgBoxDb holds the subscription topology. Together they answer the question no interview answers honestly: which of these artefacts actually carries traffic? On a fifty-application estate a meaningful slice has had none for a year. Retiring 20% of the estate is a 20% saving that no conversion improvement can match, and it is the one recommendation a client can act on the same afternoon.

Step 1 is the input nobody collects

Code cannot reveal traffic. Volumetrics must therefore come from one of three places, in strict priority: harvested from the tracking database where DB access exists; entered per flow in the UI; or defaulted with an explicitly stated range. Every downstream number is tagged with which of the three it came from. A cost model built on silent assumptions is worse than no cost model, because it will be quoted.

Steps 2–3 · archetype then constraint

Constraints that override price

Message size above 256 KB (Service Bus Standard is out — claim-check to Blob or move to Premium) · strict ordering (sessions required) · VNet or private endpoints · latency SLO · transactionality and idempotency · X12/EDIFACT/AS2 · adapter availability for SAP, MQ or HL7 · custom .NET assemblies · data residency and compliance.

Step 4 · price from a real rate card

Rates come from the Azure Retail Prices API — unauthenticated, per-region, per-SKU — multiplied by the harvested volumetrics. The model accounts for executions, actions per execution, connector-call class, storage transactions, duration and vCPU, egress and retention.

Non-negotiable rule The language model never produces a cost figure. It classifies ambiguous flows and writes the rationale; the priced model produces every number. This is what lets the output survive a CFO reading it.

Step 5 · the four levers worth encoding

  1. Enterprise connector meters are the silent budget killer. At roughly $0.001 per enterprise connector action, a SAP flow at one million messages a month costs about $1,000/month in connector charges alone — before any compute. Replacing it with a Function using a native client removes that meter entirely. Every enterprise-connector flow above a volume threshold should be flagged as a rewrite candidate.
  2. Stateful → stateless wherever the IR proves it safe. Stateful workflows write to Storage queues, tables and blobs on every action; stateless keeps state in memory. Where there are no waits, no long-running behaviour and no need for run history, default to stateless — and flag the trade-off honestly: roughly a five-minute ceiling and no run history to debug with.
  3. The Consumption ↔ Workflow Service Plan crossover sits near seven million built-in actions a month against a WS1 plan at roughly $180/month. Compute it per candidate; never apply it as a blanket policy.
  4. Bin-pack the hosts. Fifty applications do not need fifty Workflow Service Plans. Packing workflows onto shared plans — subject to blast radius, deploy cadence, scaling profile, security boundary and SLA tier — typically saves more than every per-flow service decision combined.

Step 6 · close the loop

After each wave deploys, ingest Azure Cost Management actuals and Application Insights telemetry, diff them against the estimate, and recalibrate the model's coefficients. This is what turns a one-shot migration tool into a recurring-revenue product: the estimator measurably improves with every customer, and no competitor starting later has the calibration data.

Policy, not code Express the rules as declarative, versioned YAML so each customer can tune thresholds and every recommendation is auditable after the fact. When an architect overrides a placement, capture the reason — those overrides are the training signal for the policy, and they are also the audit trail.
§ 08

Engine topology

The principle everything else depends on Engines communicate through versioned, typed artefacts in a case store — never through chat. Each engine reads named artefacts and writes its own, like a build pipeline. Agents passing prose to one another cannot be reproduced, diffed, or audited.

Every engine emits its artefact plus a confidence score and a gap list. Because artefacts are versioned, a case can be replayed or forked — "clone this at ten times the volume" — without re-running the expensive stages.

Because cost is a pure function of placement, volume and rate card, scenario analysis is free — so the interface should never show a single number. It shows a curve across volume decades and marks the point where the recommendation changes.

Illustrative rate constants — enterprise connector actions $0.001, standard connector actions $0.000125, built-in actions $0.000025, WS1 plan $180/month, Service Bus Standard base $10/month, twelve built-in and two connector actions per message. Consumption meters every action; Standard includes built-in service-provider connectors in the plan and meters only enterprise connectors; the shared plan steps up to a dedicated plan past 2M messages/month. Production pricing reads the Azure Retail Prices API for the customer's own region. This prices run cost only — engineering effort and team skills are a separate axis, which is why the cheapest curve is not automatically the recommendation a human should accept.

What the curves reveal

At default settings the recommendation flips twice, and both flips are the kind of thing a spreadsheet estimate misses. Around 17,000 messages a month the per-action Consumption meter overtakes a shared plan — so the answer stops being "pay per use" and becomes share a host you already own. Then at roughly 2.1 million the shared plan runs out of capacity, steps up to a dedicated plan, and a Function with Service Bus becomes cheapest instead.

Below that first flip, cost is almost entirely fixed — a WS1 plan, an APIM tier, an Integration Account — and per-message meters are pennies. A tool that answers "use Logic Apps, $180 a month" for a ten-thousand-message flow is giving actively harmful advice, and across fifty applications it gives it fifty times. Set the sharing divisor to 1 to see that dedicated plan lose at every volume below two million.

Now turn on the enterprise connector. The two flips collapse into one at about 7,000 messages a month, straight to the Function, because that meter applies to both Logic Apps options and to neither Function. On a high-volume SAP or MQ integration that single toggle outweighs every other placement decision — and it is invisible to any tool that does not model connector class.

§ 10

Diagram generation

Both diagrams come from the graph, not from a model's imagination. The IR dependency graph is the as-is topology; placement.json is the proposed topology. Rendering both views from one source graph is what guarantees they are genuinely comparable — the thing hand-drawn before-and-after diagrams never manage, because they are drawn months apart by different people.

Layout is deterministic: C4 / Structurizr DSL → Mermaid for the in-product view, plus draw.io XML with the Azure icon set for the stakeholder deck people actually present. The language model contributes grouping labels and narrative prose only — never node positions, never edges. An invented edge in an architecture diagram is a lie that survives review, because diagrams are trusted more than the text around them.

Diagram set per case

  • As-is topology — orchestrations, ports, adapters, MessageBox subscriptions, external systems, with dead artefacts greyed rather than deleted so reviewers can see what was retired.
  • Proposed topology — the same flows placed onto Azure services, colour-coded by service class.
  • Landing zone — the shared platform: APIM, Service Bus namespace, Key Vault, Log Analytics, Integration Account, schema and map registry, common error-handling workflow.
  • Per-flow sequence diagrams — generated from the IR action DAG, which is exactly what a DAG is for.
§ 11

UI blueprint

Governing principle The UI is a pure projection of the artefact store. No separate UI state. Every screen renders artefacts an engine has written — which is what makes closing the tab mid-run safe, and what keeps the displayed state truthful rather than optimistic.

Above the per-case screens sits a portfolio dashboard: all fifty applications with source platform, artefact counts, complexity, disposition split, estimated monthly Azure cost, effort, wave, current stage and parity percentage — plus aggregate TCO against the current BizTalk baseline. That is the only screen an executive sponsor will ever open, so it carries the number they care about.

Six states, distinguished by form as well as colour: solid ring, dashed ring, dotted ring, animated arc. Note that awaiting input and awaiting approval are brass, not red — they are the two most common real states in a human-gated pipeline, and rendering them as errors makes a working product feel broken.

Because engines run for minutes to hours

Live state over SSE or WebSocket; full resumability, so closing the tab and returning shows a truthful picture; Teams or email notification when a gate is reached, since a human-gated pipeline that nobody is watching stalls silently. Partial artefacts stream as they are produced rather than appearing only on completion.

Two cross-cutting surfaces to build early

A case audit timeline — who approved what, when, and with what override reason, where rejection reasons feed back into the policy so the product learns from being wrong. And case fork — "clone this at ten times the volume" — which is nearly free given that every artefact is already versioned, and which is the feature architects will demo to each other.

§ 12

Deterministic vs LLM

The previous generation of this tooling failed by being purely deterministic — rules cannot cover the long tail of a twenty-year-old integration estate. The obvious overcorrection is to hand everything to a model, which fails differently and less visibly. The split below is the actual design.

Where the model is allowed to operate, and where it is not.

Decompose orchestrations into smaller independently testable units; Service Bus sessions plus CorrelationId for grouping; Durable entities for aggregation. Flag every instance for human design review — never auto-convert silently.
DataWeave translation critical No DataWeave→XSLT or →Liquid converter exists anywhere. DataWeave is a full functional language, so this is language translation, not table lookup. Treat as translation with auto-generated tests: harvest real input/output payload pairs, generate a test per pair, translate, iterate until green. Where it cannot converge, emit a C# function and say so.
Transactions & compensation critical BizTalk long-running transactions with compensation blocks have no direct analogue; correctness failures here are silent and expensive. Emit an explicit saga design per case for human approval. Never generate compensation logic without a parity test that exercises the failure path.
Custom .NET pipeline components & assemblies high Often source-less; behaviour only observable through the binary. Decompile, characterise with tests derived from real traffic, rehost as a local function or Container App. Where decompilation fails, wrap and lift the binary unchanged.
Scripting functoids & complex maps high Inline C#, XSLT call-templates and database lookup functoids inside a visual map. Lift plain XSLT verbatim — the cheapest win available. Extract scripting functoids to functions. Database functoids become explicit lookup steps.
MessageBox publish/subscribe semantics high Property promotion plus filter subscriptions is a routing model, not a pipeline; it has no single Azure counterpart. Service Bus topics with subscription rules; promoted properties become message properties. Usually cheaper than the original — routing stops consuming compute.
EDI & trading-partner configuration moderate High volume of fiddly configuration; agreements, envelopes, control numbers. Mechanical migration into one shared Integration Account. Tedious rather than risky — good automation target.
Model non-determinism moderate The same input can produce different code across runs, which is unacceptable in an audited migration. Deterministic scaffolding constrains the search space; parity gates catch the rest; every generation is versioned and diffable against its predecessor.
§ 14

Verification

Nobody in this market publishes a parity number. That absence is the moat.

Industry practice on model-driven migration has converged on the same conclusion from several directions: generated code is validated by replaying real inputs and checking equivalence inside a live environment, with failures fed back to the agent — not by reading the diff and feeling reassured.

The harness

  1. Harvest golden pairs. Real input and output message pairs from the source estate — BizTalk tracking history, Mule logs. These are the specification, and they already exist.
  2. Replay locally. Functions Core Tools, Azurite and Docker reproduce the generated flow without touching Azure, so the loop is fast and free.
  3. Canonicalise, then diff. Normalise namespace prefixes, attribute order, whitespace, key order and timestamps before comparing, otherwise every diff is noise and the harness gets ignored.
  4. Score and gate. Publish parity per flow, and block promotion below threshold. A flow at 100% parity over 300 golden cases is a migration a client can sign off; a flow at 74% is a conversation.
  5. Feed failures back. The failing case, expected output and actual output go to the development agent as the next iteration's input — the environment closes the loop rather than a human transcribing it.
Why this is commercially decisive Migration projects do not stall on code generation. They stall in the six months of regression testing after it, where nobody can prove the new system behaves like the old one. A tool that arrives with 300 replayed cases per flow and a published parity score is selling the end of that six months — which is worth far more than the conversion itself.

Beyond parity

Contract tests against generated OpenAPI for anything fronted by APIM; schema validation on every emitted map; a load smoke test to confirm the placement's throughput assumption actually holds; and shadow running at cutover — BizTalk and Azure processing the same live traffic in parallel, outputs compared continuously, until the parity evidence is boring.

§ 17

Risks, open questions, sources

Risks worth naming now

  • Fidelity ceiling. Convoys, correlation sets and compensation set a hard limit on automation. The product must be honest about it in the UI, not just in the sales conversation — a tool that overclaims loses the account on the first bad orchestration.
  • DataWeave has no prior art. Budget for this as research, not as a feature, and gate it behind generated tests.
  • Microsoft owns the destination and ships a free tool. They can absorb any pure-conversion advantage. Lead with placement, economics and assurance.
  • Volumetrics access is a sales dependency. The best output requires the customer's tracking database. Design the manual-entry path to be genuinely good, not a fallback that feels like a downgrade.
  • Cost model drift. Azure pricing and SKUs change; the rate-card client and the crossover thresholds need their own regression tests, or the tool will quietly start lying.

Open questions for the next session

  • Upstream licence terms — the P0 gate on the entire fork strategy.
  • Pricing model: per application, per flow, per assessment, or a share of measured savings? The last is the most aligned and the hardest to administer.
  • Do we support Logic Apps Hybrid and on-prem targets in P1, or defer? It changes the emitter matrix and the monitoring story (OpenTelemetry rather than App Insights).
  • Is BizTalk → MuleSoft a genuine market or a positioning claim? It changes whether the IR neutrality investment pays for itself.
